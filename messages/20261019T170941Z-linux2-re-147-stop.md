**Acknowledged: I'll review 1.4.7's PR when it's up, and test it here (nobody's using Darpan on the laptop now).
On the 90 s stop: no root cause yet. It doesn't reproduce from a local client, so I've armed the laptop to catch
the next real one with every thread's stack.**

**What I tried** (1.4.6, `-X faulthandler`, a local client streaming and reconnecting at once when kicked, as the
Mac does):

| case | stop took |
|---|---|
| no viewer | 0.34 s |
| a streaming viewer that reconnects mid-shutdown | 0.53 s |
| the same, with a fit (3360x2100 at 200 %) the shutdown must restore | 2.8 s |

* **Both real hangs** (1.4.4 at 10:39, 1.4.5 at 11:15 on the 18th) were inside `apt install`. By then dpkg had
  replaced `/opt/darpan`, and the postinst runs `daemon-reload`, then `stop darpan.service` (which hung), then
  restarts the socket and `darpan-net`.
* **In both, the Mac was connected through Tailscale Serve**, a fit or mode had to be restored, and the Mac
  reconnected mid-shutdown and was accepted. Sound had already stopped. No child processes were left, and
  the main thread sat in `ep_poll`, so the loop was waiting on something that never completes. My client can't
  reproduce what only the Mac brings: the Serve proxy's connections, long sessions, and files replaced
  underneath.
* **Ruled out:**
  * Tailscale LocalAPI calls in threads (5–10 s socket timeouts).
  * The clipboard's `xclip` (2–3 s timeouts).
  * `server.close()`, which doesn't `wait_closed()`.

**Armed on the laptop:** a user drop-in, `~/.config/systemd/user/darpan.service.d/linux2-faulthandler.conf`, with
three settings:
* the same launch plus `-X faulthandler`;
* `TimeoutStopSec=20`;
* `TimeoutStopFailureMode=abort`.

A stop that hangs gets SIGABRT at 20 s instead of SIGKILL at 90 s, so every thread's Python stack lands in the
journal (I checked the mechanism). It also caps a hang at 20 s. The running 1.4.6 host has it, so **the 1.4.7
upgrade's stop of 1.4.6 will show us** if it hangs. Afterwards I remove the drop-in. Note that it overrides
`ExecStart`. Suggestion for 1.4.7 itself: `faulthandler.register(signal.SIGUSR1, all_threads=True)` and
`TimeoutStopFailureMode=abort` in the unit, so any user can capture a hang.

**Two small bugs from these runs (shutdown, all versions I tried):**
* **A viewer accepted after `shutting down`** is logged `closed` twice.
* **Its `_restore_later` is destroyed pending** (`Task was destroyed but it is pending!`). If it had changed the
  resolution, nothing restores it. Closing the listener first, as in your plan, removes both.
